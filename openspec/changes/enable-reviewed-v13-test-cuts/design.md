## Goals / Non-Goals

Qualify an explicit post-P02 foundation and replace unused initial bindings
within the existing test-only scope. Do not broaden to product/fixture/control
paths, flatten dependencies, take over owner PR edits, relax test coverage or
change settings/pins/tools/releases/sessions. No live action follows from a
draft, an enabled flag alone, shadow output or a local review.

## Decisions

1. Add an optional strict foundation epoch to the trusted projection. Pin the
   exact actual landed commit and all four foundation file blobs, not a moving
   branch or generated candidate. Require P01 ancestry, epoch ancestry to base,
   exact declared blobs and no subsequent foundation-file/mode changes. Keep
   workflow/baseline and seven P01 markers frozen from original P01. Missing
   epoch preserves the original stricter freeze. A shared data-only predicate
   serves observer contract checks and delivery configuration; no observer
   classification/output becomes a grant. Reject silent re-anchoring and
   per-request 'latest main' blob discovery as authority.
2. Recognize exactly two reviewed named test-only profiles with explicit source
   identities, bounded linear histories and complete task/file inventories.
   Replace P03/P05 with P05/P06 only after actual owner data is confirmed.
   Preserve initial-profile fixture histories so original single-child/refusal
   contracts remain tested; add revised-epoch/new-pair fixtures independently.
   Do not change any workflow jobs, commands, baseline or provider pin.
3. Count separate qualification layers honestly. Use exact-head ordinary and
   reusable source CI plus the integrated staged tree for code#100 only if its
   actual owner/config landings match that tested tree. For the revised helper,
   first find any existing matching real fixture receipt. If absent, use the
   unchanged P01 smoke-driver pattern in one separate coordinator verify branch
   on the actual landed epoch, require real start/clone/SELECT1/stop/restart
   output and compare helper blobs. Keep that driver out of product source,
   deduplicate before dispatch and never run the stale-cluster sweep on user
   benches. Engine detection or the pure contract selector is not fixture proof.
4. Final policy publication and operator admission are separate. Do not set
   the working flag true or fill missing heads/epoch during draft preparation.
   At finalization require actual immutable qualification and owner readiness,
   then exact-head full/reuse/expert/bot checks and normal merges. Lane1 alone
   edits opt-in/body/base metadata and triggers fresh source events as consented;
   body edits alone do not run the opened/synchronize/reopened CI workflows.
   Coordinate a stable canary interval with lane3 without a ruleset freeze or
   interruption of an active product candidate. Use only the named manual queue.

## Risks / Trade-offs

- Owner main/candidates advance -> recheck actual trees and epoch, discard stale
  staged evidence, and coordinate a merge window rather than reset their batch.
- New epoch could become a generic escape hatch -> strict complete inventory,
  immutable actual-main ancestry, unchanged PG workflow/baseline and independent
  real fixture qualification before reviewed policy publication.
- Existing review/fast evidence may predate retarget/enablement -> require fresh
  canonical source event/base history and actual exact-head review; no synthetic
  green status, counterfeit review or forced head change.
- Initial bindings are not scalable all-work adoption -> the first accepted pair
  is one gate, with wider task-set profiles reviewed only afterwards.

## Migration Plan

Prepare tests and bounded source changes without inventing external facts.
After the normal owner landing, verify the actual epoch and source readiness;
publish only complete checked data and leave owner edits with owners. Land the
source/config through normal checks in a safe slot, verify actual main, obtain
fresh exact-head admission consent, run the two-member canary and audit its
complete artifacts/prefixes/landing. A normal reviewed false flag is rollback;
retain full fallback and no automatic retry/failure split. Wider rollout and
assembly/session adoption are separate, not implied by this initial enablement.

## Canary-blocking regenerated merge hint amendment

Code#105 landed normally as a528e412 with its qualified source tree. Lane1's
first source events retained full because their base and generated merge hint
were stale. After live base/merge refs settled and two independent reads agreed,
the second source events still retained full solely on merge_commit_sha. Actual
GitHub objects show that each reopen regenerated the commit ID with identical
ordered parents and tree. Records6900819992/6900948064 and the route diagnostics
prove the fallback; the owner interpretation of the unlogged raw payload is
kept separate from those observed objects. No source has been enqueued.

Amend only the initial source/candidate generated-hint comparison. Missing/null
or the actual tested GITHUB_SHA still needs no extra lookup. A different hint
must be a full SHA and resolve through the existing authenticated repository
Git-commit API to that exact object with exactly the tested merge's two ordered
parents and identical tree. Bound this to at most two distinct immutable commit
reads for the two hints; cache duplicate hint identities within that comparison.
Use no added permission, credential, ref mutation, checkout or polling/retry.
API failure, unknown/malformed hint, wrong object, parent count/order/base/head
or tree retains full. Diagnostics continue to print names/reasons, not values.

The original GITHUB_SHA remains independently acquired and checked against
actual main/head ordered Git parents. Do not substitute a hint for tested
identity or align any base/head/state/author/task/admission fields. Preserve the
original byte-strict subsequent live PR rereads, authenticated fast/base-history,
review, foundation and candidate admission/full-heavy/landing requirements.
The same helper covers real source and genuine candidate-PR comparison, so the
fix does not defer the same generated-metadata defect until after admission.

Reproduce both cases with real local Git merge objects having different IDs but
equal parents/tree before changing runtime code. Cover malformed/unavailable
objects, parent/tree/identity tampering, base drift and later live hint changes.
Retain all existing nullable/current/foreign hint, candidate admission, historical
landing and coverage-parity tests. Land the narrow paired repair normally after
exact-head local expert/Codex review and ordinary full/reusable qualification.
Only then ask owners for fresh source events and exact-main consent, followed
by the original two-PR canary. Do not claim the prior full-source runs saved CI.

## Same-head canonical fast-workflow history amendment

Before admission, read-only API preflight found three genuine named fast checks
per unchanged P05/P06 head, even with filter=latest. The old global len==1 check
therefore refuses normal repeated canonical events. Rewriting an owner head to
erase that history is not an acceptable workaround. Code#107 stays draft until
this companion repair is reviewed and qualified on its updated head.

Read the configured task-set-fast.yml catalogue filtered to the exact head and
pull_request event. Require complete bounded count/list agreement (at most100),
exact repository/head/branch/path/PR-event identities, positive unique run IDs
and run_number values, and one workflow_id. Select the unique highest workflow
run_number, not API array order, check ID, run ID, completion time or any passing
result. GitHub documents run_number as increasing per workflow and unchanged
on rerun: https://docs.github.com/en/actions/reference/workflows-and-actions/variables.

Every returned named check must have the expected Actions app/head/name, exact
details URL/job identity and a unique corresponding catalogue run/check suite.
Unknown or duplicate checks retain full. Require exactly one matching check for
the selected newest run, then preserve the existing independent live run/job,
attempt, current source/base association, complete retarget history, success and
final rereads. Re-read catalogue selection before proof and refuse if a newer
canonical event appeared. Preserve the existing receipt shape and raw check/run
stability requirements; historical rows confer no permission themselves.

Older authentic failed or pending events do not supply proof or replace the
selected event. The newest failed/cancelled evidence refuses, and complete
authenticated current-job pending evidence may use only the existing bounded
observation path. A missing newest check/job remains immediate full refusal,
even when its catalogue run is pending; never add a wait grant for incomplete
evidence or fall back to an older green. Foreign, malformed, incomplete,
truncated, duplicate, mismatched or raced catalogues retain full. Use only
existing read permissions, with no workflow/job/baseline/queue/profile changes.
