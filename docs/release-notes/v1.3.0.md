# openRepoTools v1.3.0

v1.3.0 brings the SQL register (opensoft/openRepoTools#165): the lane register can live in a PostgreSQL database, with the files under `lanes/` kept as its rendered mirror. It also brings the register service, answer 2's detached bind with `start-record` in every mode, and `wip init`'s refusal under the register's marker. It is openRepoTools as it stands at `<release-commit>` in `opensoft/openRepoTools-code`, tagged on `<tag-date>`. After v1.2.0's commit, `ecd1bce7`, `<code-prs>` landed on the code leg's `main`, the last of which made that `main` `<release-commit>`, and `<spec-prs>` landed on the spec leg's `main`, in `opensoft/openRepoTools-spec`.

v1.3.0 follows v1.2.0, which shipped without feature 007: on Brett Heap's word ("v1.2.0 now, 007 later (Recommended)", 2026-11-10T13:22:23Z) the SQL register moved to the `v1.3.0` milestone. v1.2.0's notes name what shipped there, the five lane-tool fixes, the release-workflow follow-ups and the openRepoShape pin, and this release does not repeat them. The release is published from `opensoft/openRepoTools-code`, as 1.1.0 and 1.2.0 were, and its tag is made there.

The register is opt-in and dormant until an estate switches. A workstation uses it once act 4's cutover and its own flip to `mode=primary` have run, both Brett Heap's, and both waiting on the install of the server, which this release does not carry. With no `lanes-index.conf`, or with `mode=index`, every tool reads and writes as before, apart from three changes that apply in every mode: answer 2's detached bind, `start-record`, and `wip init`'s refusal.

## What v1.3.0 brings

- **The SQL register** (opensoft/openRepoTools#165). On a workstation whose `lanes-index.conf` says `mode=primary`, the register is a PostgreSQL 16 database, in a schema of its own, `lanes_register`, and the files under `lanes/` (`LANES.md`, the logs, `aliases.tsv` and `archive/`) are its rendered mirror. A workstation uses it once act 4's cutover and its own flip have run. A build without the renderer's git half refuses `mode=primary`, and says why; the tag waits for group C, whose last pull request lifts that refusal.
  - **One write is one transaction.** On a primary workstation each writing verb runs its own code unchanged on a scratch tree built at the journal's head, and its change set commits in one SERIALIZABLE transaction, or not at all. A write ends in one of five outcomes: 0; 2, a refusal, with nothing written; 3, in doubt, where the printed rerun carries `LANES_WRITE_ID` and `LANES_WRITE_GENERATION` and writes the write once, or finds it; 69, the database unreachable or refusing, with nothing written; and 75, "register busy", with nothing written, where a retry in seconds is safe. Handoffs stay git files written by the lane.
  - **Claim and hold order is commit order.** Of two claims of one object the earlier commit wins, and the later writer writes nothing and exits 2, naming the earlier line. A stale `LANDING` is released only by `append-line --landing-expired`, on Brett Heap's word.
  - **Readers decide from the database, and fail closed.** Every read that decides something reads the register's text at the head, proven by per-file digests in the same request, and runs today's parser on it. A deciding read that fails exits 69, the guard exits 2, and `managed-projection` answers 1. Only the listings and the `SessionStart` block may fall back to the mirror, and they say so with `read: mirror`.
  - **The guard answers inside its 5 s hook, whatever the database does.** The hook string and `GUARD_TIMEOUT` are unchanged. While a workstation's link to the server is down, the guard answers 2 until the link returns or an outage is declared (Brett Heap's "Block until link returns"). `lanes-index outage declare` and `outage clear` write and remove the declaration, on his word.
  - **The files are a mirror, written behind.** After each committed write, a detached renderer in the writing lane's checkout builds one commit per sequence on `origin/main`, each with a `Register-Seq` trailer, through a private index that never touches a HEAD, an index or a working tree. A commit the renderer did not make to a rendered path stops it, and it records `diverged at`; `import --single` and `render --revert` are the two ways out. On primary, `lanes-edit.sh commit`'s carry form, the hand edit, is refused with 2, and its publish of queued commits stays, fenced to `handoffs/`.
  - **The switch and the marker.** The estate's switch is a row in the database, and the marker is `lanes/STORE` on origin. Once `lanes/STORE` is on origin, a workstation that is not `mode=primary` refuses its acts with 69 and its guard with 2, and lists from the mirror. `lanes-index rollback` returns the estate to the files, byte for byte.
  - **The operator's tools** for acts 3 and 4, the rollback and the disaster path are `lanes-index bootstrap`, `login`, `ready`, `set-mode`, `import --at`, `cutover`, `rollback`, `outage declare` and `outage clear`. Each holds no secret, is idempotent where it can be, proves before it switches, and refuses rather than guess. Each engineer, human or AI host, has two logins, a writer and a reader, made by `lanes-index login`. The REGISTER-WRITER secret is readable by every lane process on its host, and the manual says so plainly.
  - **The configuration.** `lanes-index.conf` gains `mode`, `register_url`, `register_passfile`, `register_label`, `register_schema`, `render_key`, `register_addresses` and `register_rtt_ms`. A register URL carries `sslmode=verify-full` and an `sslrootcert=` that names the root of the issuer that signs the server's certificate, never `system`, and a password in it is refused; `lanes-index` refuses such a file at load, `ready`'s check 11 checks it, and the server rejects a connection without TLS. `mode=primary` with SQLite is refused.
- **The register service** (opensoft/openRepoTools#165), which the tag waits for (Brett Heap's "4A"). `lanes-index serve` is one process per environment, a bench container or a host shell, connecting as the engineer's reader login through one `psql` child. It answers the register's text at the head, proven by per-file digests, and the reader decides. The guard and the readers ask it first and read directly when it does not answer, and no write depends on it. The first call that can start it starts it, with no supervisor, on primary only: `serve` refuses with 2 in files and `index` mode. It listens on a socket in a 0700 directory of its own uid, checks each peer by `SO_PEERCRED` (`LOCAL_PEERCRED` on macOS), and stops after 15 minutes idle or when the install changes. The `SessionStart` block reads the mirror and only starts it, through `lanes-index serve --start`. The service is on the tag's path because, measured from Eagle, the guard takes about 1.2 to 2.1 s without it, over Brett Heap's 1 s, and about 0.5 to 0.7 s through it; its answer to the guard's read takes under 50 ms on the test fixture's register. The package declares no runtime dependency and no database driver: `psql` is the only client.
- **Answer 2's detached bind, and `start-record`, in every mode** (opensoft/openRepoTools#347). Today the bind that answer 2, "bind this window to that lane", starts runs inside the `UserPromptSubmit` hook, where the hook's timeout cuts it down partway, and a failed bind cannot be answered again. Now answer 2 exits 2 with "BINDING" within 0.1 s after the guard's read, and the bind runs detached, as one `guard-bind` in a `setsid` child (python3's `os.setsid` on a host without `setsid`, then `nohup` alone), under its own computed bound, 500 s at the defaults. Each prompt meanwhile gets "BINDING IN PROGRESS" and is not passed, and the next prompt after success says "MOVED". A failed bind renames the window back and keeps the offer, and choice 2 is withdrawn after the third failure. The hook string, `GUARD_COMMAND` and `GUARD_TIMEOUT` are byte-unchanged. `lanes-edit.sh` gains a write verb, `start-record`, that makes `lane-start`'s three register writes one write: one transaction on primary, and in files mode one register commit, with the handoff stamp its own commit. `lane-start --bind` is idempotent: it writes no register line again where the binding and the session cell already name this uuid.
- **`wip init` refuses under the register's marker** (Brett Heap's "Narrow it (Recommended)", 2026-11-10T16:50:07Z). `openRepoTools wip init` refuses, with exit 2 and nothing committed, wherever `lanes/STORE` exists, in every mode. Where a tree carries another file under `lanes/`, it refuses only where its seed commit would write under `lanes/`, that is, where the tree lacks `lanes/LANES.md` or `lanes/log/README.md`. The refusal names the path it found. Joining a workspace keeps working.

## What else changed since v1.2.0

- **The lane tools read through the register's verbs.** `lanes-edit.sh` gains `register-text`, `register-grep`, `act-begin`, `start-record` and `guard-bind`, and `canon-lane --walk`. `lane-start`, `lane-end`, `lane-worktrees`, `lane`, `lane-handoff` and the skills read the register through them, never by an `awk` over `$LANES_FILE` or a `git grep` of origin's branch, and in files mode their output is as before. An act takes a base with `act-begin`, and its later writes carry the scopes its reads covered: a write is refused with 2 where a journal entry made after the base, outside the act, touched one of those scopes. `lane-start`'s seven read arms refuse the launch on a 75 or a 3, naming the code, and the manual's exit table gains the clause for 3 and the row for 69.
- **The release carries check 1's list, and `--install` places it** (Brett Heap's "Release + installer (Recommended)", 2026-11-10T16:50:07Z). `openRepoTools-<release>.sha256`, in `sha256sum`'s form, is a release asset, and `openRepoTools --install` places it beside `lanes-index`. `lanes-index ready`'s check 1 reads it, and fails where it does not name both `lanes-index` and `lanes-edit.sh`.
- **`lanes-index` starts from a cached module** (Brett Heap's "(d) Both (a) and (c) (Recommended)", 2026-11-13). `lanes-index` becomes a short launcher that runs its body from `lanes_index_main.py`, a module whose bytecode Python caches, so that a start no longer compiles the whole script. Measured on cloud-bench, a start falls from 398 to 95 ms. `openRepoTools --install` places the module beside `lanes-index` and writes its checked-hash bytecode, which is never run once its source has changed; where the bytecode cannot be written, the launcher runs the source. The release's list names the module, so that check 1 digests it too. Every subcommand's argv, output and exit codes stay as they were.
- **A keyword-form `url=` refuses at load.** A `url=` in `lanes-index.conf` that is not a `postgresql://…` URL now refuses with 2, naming the URL form. The contract of opensoft/openRepoTools#160, the index half's, was always a libpq URL.
- **CI runs the register's tests on a real engine.** `tests.yml` sets `OPENREPOTOOLS_REQUIRE_PG` to 1 where the PostgreSQL 16 binaries exist, in `ubuntu-24.04` jobs, and a missing engine there fails the run and is never a skip. Without the switch the real-engine tests skip, naming `PG_BIN` and `postgresql-16`, and the fake-`psql` tests still run. The four required check names are kept. New bash holds to bash 3.2, and new Python to the standard library on Python 3.9 or later.
- **The manual** gains "The SQL register" in `docs/README-lanes.md`, beside "The derived index (Amendment 14)". It opens with "What changes for a lane", and holds the roles, the secret's reach, the socket API and the runbook for acts 3 and 4 and the rollback.
- **Everything else that landed since v1.2.0,** by area, as 1.1.0's notes list it: `<other-changes>`.

## Install and upgrade

- **From PyPI:** [openrepotools 1.3.0 on PyPI](https://pypi.org/project/openrepotools/1.3.0/) is this release's page. `pipx install openrepotools`, or `pipx install openrepotools==1.3.0` for this release, then `openRepoTools --install`, as for 1.1.0 and 1.2.0, whose notes say where `pipx` comes from and how to move to it from the one-line install. `openRepoTools --version` from the package prints five lines. The first is `openRepoTools 1.3.0 (opensoft/openRepoTools-code @ <release-commit>)`, and the other four give `version` as `1.3.0`, `tag` as `v1.3.0`, `commit` as `<release-commit>`, and `digest` as `<release-digest>` followed by `(sorted-ls-tree-r-v1)`.
- **Upgrade from 1.2.0:** `pipx upgrade openrepotools`, then `openRepoTools --install` again. Until that second command, the placed files, skills, command files and hook entries stay 1.2.0's. Run both: this release's `lane-start` reads through `lanes-edit.sh`'s `register-text`, which 1.2.0's `lanes-edit.sh` does not have, so `lane-start` and a `lanes-edit.sh` with `register-text` ship and install together. `openRepoTools --install` also places two more files beside `lanes-index`: check 1's list and `lanes_index_main.py`.
- **Nothing changes until an estate switches.** Installing this release changes no workstation's register: with no configuration, or `mode=index`, every tool reads and writes as before, apart from answer 2's detached bind, `start-record` and `wip init`'s refusal. Once the install exists, the operator's first steps, in act 3, are, in order, `lanes-index bootstrap` for the schema and the roles, `lanes-index login add` for each engineer and for the dump job, each engineer's `lanes-index.conf` with `mode=index`, `lanes-index status`, and `lanes-index ready --expect index` in every writing environment. The flip to `mode=primary` is act 4's, on his word, and `lanes-index set-mode primary` makes it once per host. The manual's runbook gives each act, word, command and owner.
- **What the register needs:** `psql` 15 or later on each workstation that uses it. `lanes-index` refuses an older one with 69, naming its version. The PostgreSQL 16 server is a CNPG `Cluster` in the codeXfactory prod install, which this release does not build.
- **Hosts that install by `./setup.sh`** get this release at the planned workBenches re-vendor, which vendors the release as a package (Brett Heap's "Vendor release as package (Recommended)", 2026-11-13): its `payload/` files plus the wheel's stamped `_release.py`, installed with `payload/openRepoTools --install`, so that check 1 keeps its meaning there. The same re-vendor carries the launcher's bare window reads of the mirror, offline (Brett Heap's "5A").
- **One install route or the other, never both,** as for 1.1.0 and 1.2.0: until opensoft/workBenches#165 lets workBenches' `scripts/setup-estate-commands.sh` accept pipx's link, a workstation uses pipx's route or workBenches' `./setup.sh`, as 1.1.0's notes describe. State at the tag, as read on `<state-read-date>`: opensoft/workBenches#165 `<workbenches-165-state>`; the install, act 3 and act 4 `<act-state>`.
- **The one-line install and a checkout** work as before, and their `--version` still prints a repository and ref and no release. They take the code leg at the commit the assembly root pins. Since `<root-bump-pr>` that is `<release-commit>`, the commit this release was built from, or a later one, so they carry this release.
- **Windows** is reached through WSL2, as for every bash command here. The package has no native Windows command, and it is a wheel only, with no source distribution.
