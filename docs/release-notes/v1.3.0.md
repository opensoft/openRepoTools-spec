# openRepoTools v1.3.0

v1.3.0 brings the SQL register (opensoft/openRepoTools#165): the lane register can live in a PostgreSQL database, with `lanes/LANES.md`, `lanes/aliases.tsv`, `lanes/archive/` and each lane log but `lanes/log/README.md` kept as its rendered mirror. It also brings the register service, answer 2's detached bind with `start-record` in every mode, and `wip init`'s refusal under the register's marker. It is openRepoTools as it stands at `<release-commit>` in `opensoft/openRepoTools-code`, tagged on `<tag-date>`. After v1.2.0's commit, `ecd1bce7`, `<code-prs>` landed on the code leg's `main`, the last of which made that `main` `<release-commit>`, and `<spec-prs>` landed on the spec leg's `main`, in `opensoft/openRepoTools-spec`.

v1.3.0 follows v1.2.0, which shipped without feature 007: on Brett Heap's word ("v1.2.0 now, 007 later (Recommended)", 2026-11-10T13:22:23Z) the SQL register moved to the `v1.3.0` milestone. v1.2.0's notes name what shipped there, the five lane-tool fixes, the release-workflow follow-ups and the openRepoShape pin, and this release does not repeat them. The release is published from `opensoft/openRepoTools-code`, as 1.1.0 and 1.2.0 were, and its tag is made there.

The register is opt-in and dormant until an estate switches. A workstation uses it once act 4's cutover and its own flip to `mode=primary` have run, both Brett Heap's, and both waiting on the codeXfactory installation of the PostgreSQL 16 CNPG server, which this release does not build. With no `lanes-index.conf`, or with `mode=index`, every tool reads and writes as before until `lanes/STORE` is on origin (see "The switch and the marker" below), apart from five changes that apply in every mode: answer 2's detached bind, `start-record`, `wip init`'s refusal, the refusal at load of a keyword-form `url=`, and a failed register read, which ends 69 and writes nothing, since `lane-start` and `lane-end` read the register through `lanes-edit.sh register-text` in every mode.

## What v1.3.0 brings

- **The SQL register** (opensoft/openRepoTools#165). On a workstation whose `lanes-index.conf` says `mode=primary`, the register is a PostgreSQL 16 database, in a schema of its own, `lanes_register`, and `lanes/LANES.md`, `lanes/aliases.tsv`, `lanes/archive/` and each lane log but `lanes/log/README.md` are its rendered mirror. A workstation uses it once act 4's cutover and its own flip have run.
  - **One write is one transaction.** On a primary workstation each database-backed writing verb reuses its existing edit path on a scratch tree built at the journal's head, and its change set commits in one SERIALIZABLE transaction, or not at all; `rename-lane` moves and stamps its handoff after COMMIT, and `commit`'s hand-edit form is refused. A write that reaches the database ends in one of five outcomes: 0; 2, a refusal by the register's own rules, with nothing written; 3, in doubt, as when the connection fails at the commit, where the printed rerun carries `LANES_WRITE_ID` and `LANES_WRITE_GENERATION` and writes the write once, or finds it (where an identical write is still being started, the note names its pid and the check to make once it ends); 69, the register unreadable before the commit, or the database refusing the write, with nothing written; and 75, "register busy", with nothing written, where a retry in seconds is safe. A verb's own refusal before that keeps its existing code. Handoffs stay git files written by the lane.
  - **Claim and hold order is commit order.** Of two claims of one object the earlier commit wins, and the later writer writes nothing and exits 2, naming the earlier line when the refusal's follow-up read succeeds. A stale `LANDING` is released only by `append-line --landing-expired`, on Brett Heap's word.
  - **Readers decide from the database, and fail closed.** Outside the explicit mirror cases, every read that decides something reads the register's text at the head, proven by per-file digests in the same request, and runs the same parser as before on it. A deciding read that fails exits 69; the guard's failed prefetch exits 2, while a failed second read leaves that log unread and does not by itself refuse the prompt; `managed-projection` answers 1. The listings `lanes` and `history` when the database is unreachable, the `SessionStart` block, the launcher's offline window reads, and the naming and ownership reads of `lane-handoff` and the handoff skill may read the mirror as their requirements specify. On primary, the `lanes` footer names the store that answered, the register at its seq or the mirror; where the register did, it claims no local read. The guard may answer from the mirror only during a qualifying declared outage: its database read failed or found the switch at `files`, the declaration is present, unexpired and names this workstation's database, and the mirror's `Register-Seq` is at least the one the declaration records. Every mirror read says `read: mirror`.
  - **The guard answers inside its 5 s hook, in each of three failure shapes.** The hook exits 2 inside its 5 s for a database address whose connect never completes, a listener that never speaks, and a read held behind a lock (SC-003). The hook string and `GUARD_TIMEOUT` are unchanged. While the guard's prefetch cannot read the database, as when a workstation's link to the server is down, the guard answers 2 until the link returns or an outage is declared and the conditions above hold (Brett Heap's "Block until link returns (Recommended)"). `lanes-index outage declare` and `outage clear` write and remove the declaration, on Brett Heap's word.
  - **The files are a mirror, written behind.** After each committed write, a detached renderer in the writing lane's checkout catches up every missing non-operator sequence on `origin/main`, one commit per sequence, each with a `Register-Seq` trailer, through a private index that never touches the lane checkout's HEAD, index or working tree. It does not render the cutover or rollback operator entry: the command that wrote that entry pushes and confirms its own `lanes/STORE` commit. A commit the renderer did not make to a rendered path stops it, and it records `diverged at`; `import --single` and `render --revert` are the two ways out. On primary, `lanes-edit.sh commit`'s carry form, the hand edit, is refused with 2. Its publish of queued commits remains, fenced to `handoffs/`: a commit whose every path is `lanes/repos.tsv` or `lanes/log/README.md`, added or modified as a regular file, is also let through, any other queued commit under `lanes/` is refused as a divergence, and a commit holding either of those two files beside any other path is refused with 2.
  - **The switch and the marker.** The estate's switch is a row in the database, and the marker is `lanes/STORE` on origin. Once `lanes/STORE` is on origin, a workstation that is not `mode=primary` refuses its acts with 69 and its guard with 2, and lists from the mirror. `lanes-index rollback` returns the estate to the files, byte for byte.
  - **The operator's tools** for acts 3 and 4, the rollback and the disaster path are `lanes-index bootstrap`, `login`, `ready`, `set-mode`, `import --at`, `cutover`, `rollback`, `outage declare` and `outage clear`. Each holds no secret, is idempotent where it can be, proves before it switches, and refuses rather than guess. Each engineer, human or AI host, has two logins, a writer and a reader, made by `lanes-index login`. The REGISTER-WRITER secret is readable by every lane process on its host, and the manual says so plainly.
  - **The configuration.** `lanes-index.conf` gains `mode`, `register_url`, `register_passfile`, `register_label`, `register_schema`, `render_key`, `register_addresses` and `register_rtt_ms`. A real off-loopback TCP register URL carries `sslmode=verify-full` and an `sslrootcert=` that names the root of the issuer that signs the server's certificate, never `system`, and a password in any URL is refused. `lanes-index` refuses at load an off-loopback TCP URL that lacks those values, `ready`'s check 11 checks them, and the server rejects a connection without TLS; a Unix-socket or loopback URL is allowed without TLS, for fixtures and stand-ins. `mode=primary` with SQLite is refused.
- **The register service** (opensoft/openRepoTools#165), which the tag waits for (Brett Heap's "4A"). `lanes-index serve` is one process per environment, a bench container or a host shell, connecting as the engineer's reader login through one `psql` child. It answers the register's text at the head, proven by per-file digests, and the reader decides. The guard's prefetch and the ordinary register readers ask it first and read directly when it does not answer. Where the guard read directly, it prints `guard: direct (service unavailable)`, and `lanes-index status` gains a `service:` line in every mode and, on primary, the service's failure stamp where one is held. The guard's second read always reads directly, and the `SessionStart` block reads the mirror and only starts the service, through `lanes-index serve --start`. No write depends on it. The first call that can start it starts it, with no supervisor, on primary only: `serve` refuses with 2 in files and `index` mode. It listens on a socket in a 0700 directory of its own uid, checks each peer by `SO_PEERCRED` (`LOCAL_PEERCRED` on macOS), a check that the tests exercise only through a stand-in on Linux and not at all on macOS, and stops after 15 minutes idle or when the install changes. The service is on the tag's path because, measured from Eagle, the guard takes about 1.2 to 2.1 s without it, over Brett Heap's 1 s, and about 0.5 to 0.7 s through it. The release's own run records its answer to the guard's read at a warm p95 of `<service-p95-ms>` ms, measured from the client's connect to the last byte of a digest-checked answer on a scratch database on a PostgreSQL 16 workstation and rounded up to whole milliseconds, where the release requires under 50 ms. The package declares no runtime dependency and no database driver: `psql` is the only client.
- **Answer 2's detached bind, and `start-record`, in every mode** (opensoft/openRepoTools#347). Before v1.3.0 the bind that answer 2, "bind this window to that lane", starts runs inside the `UserPromptSubmit` hook, where the hook's timeout cuts it down partway, and a failed bind cannot be answered again. In v1.3.0 answer 2 exits 2 with "BINDING" within 0.1 s after the guard's read, and the bind runs detached as one `guard-bind` child: under `setsid` where it exists, otherwise python3's `os.setsid`, otherwise, on a host with neither `setsid` nor python3, `nohup` alone, which survives a hangup but not a process-group kill (a gap Brett Heap accepted). With `timeout`, its body runs under its computed bound, 500 s at the defaults; without `timeout`, its record says `bounded=no`, the body has no whole-bind bound, and each register call remains bounded, while git network and local hangs do not. Each prompt meanwhile gets "BINDING IN PROGRESS" and is not passed, and the next prompt after success says "MOVED". A failed bind renames the window back and keeps the offer, and choice 2 is withdrawn after the third failure. Where an attempt left its `start-record` write in doubt, the next answer 2's bind looks that write up in the register before it binds again. The bind's record, the offer file in its four modes, with each key and the phase that writes it, is specified in feature 007's `contracts/bind-record.md`. The hook string, `GUARD_COMMAND` and `GUARD_TIMEOUT` are byte-unchanged. `lanes-edit.sh` gains a write verb, `start-record`, that makes `lane-start`'s three register writes one write: one transaction on primary, and in files mode one register commit, with the handoff stamp its own commit. `lane-start --bind` is idempotent: it writes no register line again where the binding and the session cell already name this uuid.
- **`wip init` refuses under the register's marker** (Brett Heap's "Narrow it (Recommended)", 2026-11-10T16:50:07Z). `openRepoTools wip init` refuses, with exit 2 and nothing committed, wherever `lanes/STORE` exists, in every mode. Where a tree carries another file under `lanes/`, it refuses only where its seed commit would write under `lanes/`, that is, where the tree lacks `lanes/LANES.md` or `lanes/log/README.md`. The refusal names the path it found. Joining a workspace keeps working.

## What else changed since v1.2.0

- **The lane tools read through the register's verbs.** `lanes-edit.sh` gains `register-text`, `register-grep`, `act-begin` and `start-record`, and `canon-lane --walk`. `lane-start`, `lane-end`, `lane-worktrees`, `lane`, `lane-handoff` and the skills read the register through them, never by an `awk` over `$LANES_FILE` or a `git grep` of origin's branch, and in files mode their output is as before, but for `lane-start`'s bind, which is now `start-record`'s one commit. An act takes a base with `act-begin`, and its later writes carry the scopes its reads covered: on primary a write is refused with 2 where a journal entry made after the base, outside the act, touched one of those scopes; in files mode the base and the scopes are ignored. `lane-start`'s seven read arms refuse the launch on a 75 or a 3, naming the code, and its move onto `start-record` adds more read arms, the act base and, on primary, the walk among them, which refuse the launch before anything is written on a 69, a 75 or a 3. For `start-record` itself, any 2 under a sequence base stops the launch. Under `@files`, a new-row 2 also stops; a resume or existing-row 2 first re-runs `act-begin`; where the base is still `@files` it prints the writer's note, writes the Rule 3 stamp for a resume, and lets the launch go on; where the base is now a sequence base it stops with 2, and where the re-run fails it refuses, before any stamp. The new-row form refuses the launch on 69, 75 or 3; a resume or existing-row form prints the writer's note or rerun, writes the stamp for a resume and lets the launch go on; and `lane-start --no-launch --bind` refuses every nonzero result. The manual's exit table gains the clause for 3, which lands as a spec-leg row beside the in-doubt rule's code pull request, and the row for 69.
- **The release carries check 1's list, and `--install` places it** (Brett Heap's "Release + installer (Recommended)", 2026-11-10T16:50:07Z). `openRepoTools-<release>.sha256`, in `sha256sum`'s form, is a release asset, and `openRepoTools --install` places it beside `lanes-index`. `lanes-index ready`'s check 1 reads it, and fails where it does not name both `lanes-index` and `lanes-edit.sh`.
- **`lanes-index` starts from a cached module** (Brett Heap's "(d) Both (a) and (c) (Recommended)", 2026-11-13). `lanes-index` becomes a short launcher that runs its body from `lanes_index_main.py`, a module whose bytecode Python caches, so that on Python 3.11 and later a start no longer compiles the whole script. Measured on cloud-bench with Python 3.12.3, under other lanes' load, a start falls from 398 ms to 95 ms as a precompiled file, and to 92 ms through the launcher this release uses (medians); Python 3.9 and 3.10 keep v1.2.0's start-up. `openRepoTools --install` places the module beside `lanes-index` and, on 3.11 and later, writes its checked-hash bytecode, which is never run once its source has changed; where the bytecode cannot be written, the launcher runs the source. The release's list names the module, so that check 1 digests it too. On Python 3.9 and 3.10 the install writes no bytecode and the launcher runs the source; check 1 compares bytes on 3.11 and later only, and there only where `sys.implementation.cache_tag` is not None (where it is None, on any version, the module has no bytecode path, so check 1 compares no bytes, and reports the source path and passes), and on 3.9 and 3.10 it reports the source path and passes. On 3.11 and later, check 1 also recompiles the module, and fails unless the installed bytecode equals it, byte for byte. On Python 3.11 and later, `openRepoTools --install` again repairs a stale cache on an interpreter whose output is byte-stable. Every subcommand's argv, output and exit codes stay as they were.
- **A keyword-form `url=` refuses at load.** A `url=` in `lanes-index.conf` must be a libpq URI beginning `postgresql://` or `postgres://`; a keyword/value connection string now refuses with 2 at load, naming the URL form. The contract of opensoft/openRepoTools#160, the index half's, was always a libpq URL.
- **CI runs the register's tests on a real engine.** `tests.yml` sets `OPENREPOTOOLS_REQUIRE_PG` to `1` once, in its workflow-level `env:`, so it reaches all four jobs, `guard-launch-mode`, `tests`, `tests-no-submodule` and `package`, each on `ubuntu-24.04`, whose image carries PostgreSQL 16. With the switch at 1, pytest exits 4 where no usable PostgreSQL 16 engine is found, even in a job that selects no real-engine test, so a missing engine fails the run and is never a skip. Unset or 0, a missing engine makes the real-engine tests skip, naming `PG_BIN` and `postgresql-16`, and the fake-`psql` tests run everywhere. The four job names are kept. New bash holds to bash 3.2, and new Python to the standard library on Python 3.9 or later.
- **The manual** gains "The SQL register" in `docs/README-lanes.md`, beside "The derived index (Amendment 14)". It opens with "What changes for a lane", and holds the roles, the secret's reach, the socket API and the runbook for acts 3 and 4 and the rollback.

    digest    <release-digest> (sorted-ls-tree-r-v1)

- **Upgrade from 1.2.0:** `pipx upgrade openrepotools`, then `openRepoTools --install` again. Until that second command, the placed files, skills, command files and hook entries stay 1.2.0's. Run both: this release's `lane-start` reads through `lanes-edit.sh`'s `register-text`, which 1.2.0's `lanes-edit.sh` does not have, so `lane-start` and a `lanes-edit.sh` with `register-text` ship and install together. `lane-end`, `lane-worktrees`, `lane` and `lane-handoff` also read through the register's verbs, so they too need the `lanes-edit.sh` that has those verbs. `openRepoTools --install` also places two more files beside `lanes-index`: check 1's list and `lanes_index_main.py`.
- **The SQL register stays dormant until an estate switches.** Installing this release changes no workstation's register: with no configuration, or `mode=index`, every tool reads and writes as before until `lanes/STORE` is on origin (see "The switch and the marker" above), apart from answer 2's detached bind, `start-record`, `wip init`'s refusal and the refusal at load of a keyword-form `url=`. Once the install exists, the operator's first steps, in act 3, are, in order, `lanes-index bootstrap` for the schema and the roles, `lanes-index login add` followed by the engineer's name for each engineer, and `lanes-index login add --dump-job` for the dump job, each engineer's `lanes-index.conf` with `mode=index`, `lanes-index status`, and `lanes-index ready --expect index --release 1.3.0 --env` followed by each environment's own label, in every writing environment. The flip to `mode=primary` is act 4's, on Brett Heap's word, and `lanes-index set-mode primary` makes it once per host. The manual's runbook gives each act, word, command and owner.
- **What the register needs:** on each workstation that uses it, register subcommands require `psql` 15 or later, while `lanes-index ready` check 2 requires `psql` 16 before a workstation flips to primary. Ordinary register calls refuse an older client with 69, naming its version; `journal --write-id` exits 3, and `serve` stamps `no-psql` and exits 2. Each such workstation also needs `git` 2.32 or later, which `lanes-index ready`'s check 14, run last, requires. The PostgreSQL 16 server is a CNPG `Cluster` in the codeXfactory prod install, which this release does not build.
- **Hosts that install by `./setup.sh`** get this release at the planned workBenches re-vendor, which vendors the release as a package (Brett Heap's "Vendor release as package (Recommended)", 2026-11-13): its `payload/` files plus the wheel's stamped `_release.py`, installed with `payload/openRepoTools --install`, so that check 1 keeps its meaning there. The same re-vendor carries the launcher's bare window reads of the mirror, offline (Brett Heap's "5A").
- **One install route or the other, never both,** as for 1.1.0 and 1.2.0: until opensoft/workBenches#165 lets workBenches' `scripts/setup-estate-commands.sh` accept pipx's link, a workstation uses pipx's route or workBenches' `./setup.sh`, as 1.1.0's notes describe. State at the tag, as read on `<state-read-date>`: opensoft/workBenches#165 `<workbenches-165-state>`; the install, act 3 and act 4 `<act-state>`.
- **The one-line install and a checkout** work as before, and their `--version` still prints a repository and ref and no release. They take the code leg at the commit the assembly root pins. After `<root-bump-pr>`, that pin is `<release-commit>` or a later commit, so they carry this release.
