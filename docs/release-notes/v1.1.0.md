# openRepoTools v1.1.0

v1.1.0 puts openRepoTools on PyPI. It is openRepoTools as it stands at `2a057a6d84e58c8acb4bda20d2b7b667b552c3fe` in `opensoft/openRepoTools-code`, tagged on 2026-10-28. `pipx install openrepotools` is a second way in, beside the one-line install and a checkout's `--install`, and `openRepoTools --version` from the package names the release it runs. 60 pull requests landed between v1.0.0's commit, `aaa7bc8`, and this release's: 59 on `main` in `opensoft/openRepoTools`, up to `33ce26d`, the commit the triad's legs were carved from, and then opensoft/openRepoTools-code#1 on the code leg's `main`. The split itself, opensoft/openRepoTools#344, which made `opensoft/openRepoTools` the triad's assembly root, landed there after them and is not one of the 60.

v1.0.0 is not on PyPI, and 1.1.0 is the first version there. This release is published from `opensoft/openRepoTools-code`, after the triad migration (opensoft/openRepoTools#186), and its tag is made there. v1.0.0 stays in `opensoft/openRepoTools`, where it was made, and no tag is carried from one repository to the other.

## What 1.1.0 adds

- **openRepoTools on PyPI, as `openrepotools`** (opensoft/openRepoTools#228). <https://pypi.org/project/openrepotools/1.1.0/> is its page. Two commands install it:

  ```sh
  pipx install openrepotools
  openRepoTools --install
  ```

  The package places one command, `openRepoTools`. It runs the packaged `openRepoTools` with the first `bash` on your `PATH` and your arguments unchanged, and with no `bash` it refuses and names it. It needs Python 3.9 or newer and declares no Python dependencies. The toolset's own requirements are unchanged: `bash`, `git`, and `jq` for `--install`.

  The wheel carries everything `--install` places, the sixteen commands and `repos.tsv`, the three skills and the three command files, and the openRepoShape pin, each byte for byte as the release commit holds it. So `openRepoTools --install` run from the package reaches no network. pipx owns `openRepoTools` in its bin directory, `~/.local/bin` by default, as a link into its own environment, and `--install` leaves that one link alone: it places the other sixteen, says `1 left to pipx`, and writes 28 receipt rows where a full install writes 29.

  The version is the tag's, and no file in the repository carries a version number: the release build stamps it into the wheel.
- **`--version` names the release** (opensoft/openRepoTools#228). From the package it prints five lines:

  ```text
  openRepoTools 1.1.0 (opensoft/openRepoTools-code @ 2a057a6d84e58c8acb4bda20d2b7b667b552c3fe)
    version   1.1.0
    tag       v1.1.0
    commit    2a057a6d84e58c8acb4bda20d2b7b667b552c3fe
    digest    31123e2d08efe36583e72956ed8b8dbbe4b968c75402b59af5b8952be83ef6d5 (sorted-ls-tree-r-v1)
  ```

  A package built outside a release prints `openRepoTools 0.0.0 (an unstamped package)` and says so. A checkout and the one-line install print a repository and ref, as in v1.0.0, and no version number: a checkout's ref is `main` by default, and the one-line install, which since the triad migration (opensoft/openRepoTools#186) runs through the assembly root's front door, names the `opensoft/openRepoTools` commit it resolved `main` to. A package whose stamp is broken refuses every invocation, `--help` included, and names the fix, `pipx reinstall openrepotools`.
- **`--install` meets each other installer by a rule** (opensoft/openRepoTools#228):
  - pipx's link is skipped, by whichever `--install` meets it: the package's, a checkout's or the one-line install's. A checkout's or the one-line install's count line then says where the other sixteen now come from.
  - pip's console script at the target `openRepoTools`, which `pip install --user openrepotools` leaves, is refused in every mode before anything is placed, and the refusal names pipx as the one package route.
  - Any other link at a target still refuses the whole install, and no refusal advises removing pipx's link.
  - After a package-mode install, a note names the first `openRepoTools` on your `PATH` when it is not the package's, so a stale bash file ahead of pipx's link is not mistaken for the release.
- **The hook pair waits for its target** (opensoft/openRepoTools#237, opensoft/openRepoTools#247). `openRepoTools --install` and `openRepoTools wip init` add the pair of hook entries, `SessionStart` and the name guard (`guard`), to `~/.claude/settings.json` only once `~/projects/xFactory/lanes-edit.sh` exists, is executable and answers `guard`. Until then they say why, and how to complete it, and our exact guard entry is taken back out of a file that already carries it; our `SessionStart` entry, which ends in `|| true`, and every hook of yours stay. So a workstation upgrading from v1.0.0 whose `~/projects/xFactory/lanes-edit.sh` does not answer `guard` loses that one entry on its next `--install`, until `openRepoTools wip init`, or `link-estates` and `--install` again, completes the pair. Before this, a fresh workstation got both entries before workspace initialization had provided that file, so the name guard could fail with a command-not-found error at every prompt.
- **CI proves the package, and a release workflow publishes it** (opensoft/openRepoTools#228).
  - `tests.yml` runs on every push to `main` and to every `release/v*` branch, as well as on pull requests, nightly and by dispatch, and every run has four jobs: `guard-launch-mode`, `tests`, `tests-no-submodule` and `package`. The `package` job builds the wheel twice at the commit's time and requires the two to be one file, checks every packaged payload file against the commit's blob in bytes and in mode, checks the wheel's `.dist-info`, installs the wheel with pipx, runs the unstamped `--version` and an offline `--install` beside pipx's link, and runs the package's tests, failing if one is skipped.
  - `release.yml` is run by hand, on an annotated tag, with the version. It is adapted from openRepoShape v1.1.0's. Its build refuses unless the ref is the version's annotated tag and the tag names the run's commit; that commit is on `main` or on `release/vX.Y`; the `testpypi` and `pypi` environments each name a required reviewer and limit deployments to `v*` tags; the commit's four CI jobs ran in a push or dispatch run of `tests.yml` and the newest succeeded; and the tree digest computed here equals the one computed from GitHub's tree listing. It then builds twice from `git archive`, stamps the build, and requires one file.
  - It uploads by trusted publishing, with no token: to TestPyPI, then an install check on Ubuntu, on macOS (run again under macOS's own bash 3.2) and on Ubuntu with Python 3.9, then to PyPI. Each upload waits for Brett Heap's approval in its environment. A pre-release `X.Y.ZrcN` reaches TestPyPI only. Only `opensoft/openRepoTools-code` may publish a final version, and nothing uploads to PyPI from `opensoft/openRepoTools`.
- **Releases are annotated tags** (opensoft/openRepoTools#228). A release is an annotated tag `vX.Y.Z` on a commit on `main` or on `release/vX.Y`, never a branch and never a version number committed to a file, and a tag is never moved or reused. `release/vX.Y` is cut at `vX.Y.0` and carries the patch tags. A fix lands on `main` first, then reaches the release branch by a fast-forward, a merge, or a pull request of `git cherry-pick -x`. A version is uploaded once, and a bad upload is fixed by the next patch.
- **The lane tools name what they could not read in a triad's legs** (opensoft/openRepoTools#255, opensoft/openRepoTools#271). It closes two gaps in opensoft/openRepoTools#246, which taught the lane tools to look inside a triad's legs; each broke that change's rule that a read that failed is never an empty one. `lane-handoff` names every tree-inventory record that is not a whole schema-1 one in its NOT POLLED note, and the lane stays SWAPPING. A leg directory this account cannot search is unreadable and never `absent`: `lane-worktrees sweep` exits 3, `lane-end` refuses over it, `lane-reconcile` gives it an `unreadable` row, and `lane-handoff` withholds its tree. A dependency nested in a leg is unreadable to the sweep too where this account cannot search its directory, or a directory above it inside the leg: the sweep exits 3, and `lane-end` refuses over it. A leg directory that is not there at all is still `absent`. A known gap remains (opensoft/openRepoTools#272): the sweep also reads a declared leg beneath a directory this account cannot search as `absent`, so `lane-end` does not hold on it. These readers run only in an assembly, a checkout whose `project.yaml` declares a leg, so a checkout with no `project.yaml` sees no change.
- **`lane-handoff` reads the lane's lifecycle whole** (opensoft/openRepoTools#280, opensoft/openRepoTools#283). It used to pipe `lanes-edit.sh lane-state` into an `awk` that exits as soon as it has printed the one field it wants. Under `pipefail`, a `lane-state` that wrote again after that died of SIGPIPE, so now and then the read exited 141, the handoff said the lifecycle could not be read, and it recorded no RUNNING to SWAPPING to SWAPPED transition. That failed safe, but whether it happened depended on timing alone, and it could turn a pull request's `tests` job red at random. The handoff now takes `lane-state`'s whole output first and parses it afterwards, so its status is `lane-state`'s own. The read of the operation of a lane that is still SWAPPING, which only names that operation in a note, is made the same way.

## What else changed since v1.0.0

- **The estate commands** (`park`, `resume` and `status`):
  - `resume` and `status` hold each leg to the branch bootstrap puts it on: the leg row's own `branch:`, else the root's `tracking_branch` (opensoft/openRepoTools#238).
  - `park`, `resume` and `status` find a family folder named for its repository or for its display name, and `resume` names the holder's repository from `family.yaml` where it is on disk (opensoft/openRepoTools#240).
  - `park`'s not-carried report counts a leg's unpushed commits on the branch its own row declares, else the root's `tracking_branch` (opensoft/openRepoTools#249).
  - `family.yaml` values are read the way openRepoShape v1.1.0 reads them, `status` names one family laid out twice, and `resume` finds a holder by its id when its record names another folder (opensoft/openRepoTools#251).
- **The register and `lanes-edit.sh`:**
  - `swapped` names a lane by the register row's spelling, not the log file's (opensoft/openRepoTools#201).
  - `superseded_by` follows a chain of TAKEOVERs to its last link, so one lane holds the object (opensoft/openRepoTools#204).
  - The lane listing reads a row's state phrase when its log is missing, so a migrated PAUSED row stops showing NO LOG (opensoft/openRepoTools#206).
  - `managed-projection` reads this checkout's row as the writers do, `lane-trees` tells an unlistable trees directory from no inventory, and the manual's seven-column row is qualified (opensoft/openRepoTools#213).
  - `lanes-edit.sh commit` with nothing staged still publishes the local commits that origin lacks, when each of them only adds or changes a register or handoff file, so the recovery's re-run of `commit` pushes the edit it stranded, and the conflict recovery warns that `reset --hard` drops a peer's commits (opensoft/openRepoTools#214).
  - A one-line record cannot take a newline: `append-line` and `lane-handoff`'s why refuse it before writing, and the deferred `lane-start` command keeps `--agent` (opensoft/openRepoTools#218).
  - `lanes-index` follow-ups: `export` reads one snapshot, `history --index` says its closing stderr count, a foreign source is refused before the lock, a damaged table reads as unusable, an unread lane stays NOT READ in the index, and the worktrees footer names the workstation (opensoft/openRepoTools#219).
  - A register that could not be read no longer reads as a lane with no session ids, so the dead-lane `--force` check and `duplicate-holder` fail closed (opensoft/openRepoTools#221).
  - Register sweeps and reads refuse what they could not read: `retire-rows`, `archive-rows`, `migrate-state-cells`, the DORMANT class, `next-free` and `add-row` (opensoft/openRepoTools#230).
  - Lifecycle reads that failed are no longer answers, `set-lane-tree`'s fence closes with its operation, and a lane sidecar is valid only when whole (opensoft/openRepoTools#252).
  - The register's rewrites refuse a copy or write they cannot prove and put a cut-short register back, `retire-rows` refuses an unpushed log rename before it writes and calls a lane closed only from its published log, and `add-row` refuses an archive row it cannot read and takes back a row refused after its rebase (opensoft/openRepoTools#263).
  - A lane listing that is not whole no longer removes indexed worktree rows: the inventory read says PARTIAL, `lanes --worktrees` prints it NOT WHOLE, and `lanes-index` writes nothing over it; an older helper's tree with no path stays a tree (opensoft/openRepoTools#289).
- **`lane`, `lane-start`, `lane-end`, the name guard and their helpers:**
  - `lane-end`'s synopsis says what a DUPLICATE retire does, a state cell that breaks the phrase's grammar is read whole instead of narrowed, and the TAKEOVER grammar table and two `tests.yml` header comments are corrected (opensoft/openRepoTools#202).

## Install and upgrade

- **From PyPI:** `pipx install openrepotools`, or `pipx install openrepotools==1.1.0` for this release, then `openRepoTools --install`. `pipx` itself comes from `sudo apt-get install -y pipx` on Debian and Ubuntu and `brew install pipx` on macOS; then run `pipx ensurepath` and open a new terminal. The package is tested against the layouts of pipx 1.11.1, 1.17.8 and 1.18.3. `openRepoTools --version` prints the five lines above.
- **From the one-line install to pipx:** run

  ```sh
  pipx install --force openrepotools
  openRepoTools --install
  ```

  `--force` is needed. The one-line install left a regular file at `~/.local/bin/openRepoTools`, and a plain `pipx install openrepotools` meets it: pipx only warns that the file exists and that it is not modifying it, places no link, and exits 0. The bash file stays at that path and keeps running, so `--version` still names a repository and ref and not a release, and its next `--install` finds no payload beside it and fetches `main`. `--force` puts pipx's link in the file's place. Then `openRepoTools --install` skips that link and replaces the other sixteen files with the package's. On a workstation with no `openRepoTools` yet, `pipx install openrepotools` is enough.
- **Upgrade:** `pipx upgrade openrepotools`, then `openRepoTools --install` again. Until that second command, the placed files, skills, command files and hook entries stay the earlier release's, and the link is skipped again.
- **Remove:** `pipx uninstall openrepotools` removes only the command and its environment. The placed files, the skills, the command files, the hook entries and the receipt stay, and a checkout's `--install` then places a regular `openRepoTools` at the freed path.
- **One install route or the other, never both.** Until opensoft/workBenches#165 lets workBenches' `scripts/setup-estate-commands.sh` accept pipx's link, a workstation uses pipx's route or workBenches' `./setup.sh`. `./setup.sh` refuses a symlinked `openRepoTools` before it installs anything, and after installing it requires a regular file identical to its vendored copy, so on a workstation with pipx's link every `./setup.sh` refuses its estate step and names the link. This is Brett Heap's option (c), of 2026-10-18. State of opensoft/workBenches#165 at the tag: open, and not landed, as read on 2026-10-28.
- **The one-line install and a checkout** work as before, and their `--version` still prints a repository and ref and no release: a checkout's ref is `main` by default, and the one-line install's is now the `opensoft/openRepoTools` commit that the assembly root's front door resolved `main` to.
- **Windows** is reached through WSL2, as for every bash command here. The package has no native Windows command, and it is a wheel only, with no source distribution.
